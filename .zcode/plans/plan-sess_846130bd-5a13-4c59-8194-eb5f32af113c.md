# Flow telemetry → stat: run-scoped step logging, "flow" timeline step, pre-action runs

## Context

The v1.0.42 deploy was lost silently: Vercel killed the webhook at its default 10s while the safe version check hung, and nothing was visible in stat (flow's error events carry no `workflowRunId`, and stat's `fetchDeployRuns` filters `workflowRunId IS NOT NULL` — so they never appear as runs). The Vercel timeout stays at 10s (free tier), so instead we replicate serf's telemetry mechanics in flow and teach stat to show it:

- **flow**: accumulate a run-scoped context (steps + fork data), send `FLOW_START` at start, `FLOW_END`/`FLOW_ERROR` with all data — fire-and-forget, short timeouts, never blocks the deploy.
- **stat**: new first timeline step "flow" (like the existing master-github-action step) with chips of passed flow steps; runs list shows a run **before** the GitHub Action starts (no run id, no redeploy button); once the real master run appears, the flow events merge into its timeline.

Serf's pattern to replicate (deploy_v2.yml:114-134, 1473-1520): `steps: string[]` accumulated per milestone → `POST {STAT_URL}/add-event` with `{projectId, namespace, stage, eventData, steps, isError}` at START (empty steps) / END (filled) / ERROR (`isError:true`).

## Part A — flow (`back/`)

1. **New `back/src/runContext.ts`** — `createFlowRun({ repo_name, namespace, tag, commit })` returning:
   - `steps: string[]` + `step(name)` (push milestone tag),
   - `data: Record<string, unknown>` + `note(key, value)` (fork data: safe attempt count/latency/version, chosen workflow file, dispatch duration),
   - `sendStart()` / `sendEnd()` / `sendError(err)` → axios POST `{STAT_URL}/add-event` with `stage: FLOW_START|FLOW_END|FLOW_ERROR`, `projectId: '<repo>@github'`, `eventData: JSON.stringify({tag, commit, ...data})`, `steps`, `isError` — **timeout 3s, never awaited on the hot path** (catch + console only), mirroring serf's "telemetry never fails the deploy".
2. **Wire into `back/src/webhook.ts`** — one run per namespace (stat runs are per project+namespace):
   - In `handleTag`'s namespace loop: create the run (steps so far: `webhook-received`, `signature-verified`, `tag-parsed`, `prev-tag-resolved`, `namespaces-resolved`), `sendStart()` immediately — this is the "one stat request on start".
   - In `triggerWorkflow`: `step('safe-version')` + notes (attempts, latency, version), `step('dispatch')` + note (workflow file); `sendEnd()` after the `by:` log; `sendError()` in both catches (version-check throw → outer handleTag catch → run error send; dispatch catch replaces the current `DEPLOY`-stage `sendRuntimeErrorToStat`).
   - Pre-namespace failures (signature/tag validation) keep today's `WEBHOOK_VALIDATION`/`TAG_VALIDATION` error events — no run, no namespace to key on.
3. **Re-cap the safe budget for the 10s ceiling** — `SAFE_VERSION_TOTAL_BUDGET_MS: 45_000 → 6_000` in webhook.ts (~1.5s prelude + 6s safe + ≤1s dispatch + telemetry fits in 10s; a cold safe@render now fails closed *visibly* via FLOW_ERROR instead of being killed silently). Update the paired comment + DECISIONS.md (supersedes the 2026-11-27 "raised-to-60s" pairing note — the dashboard change is officially off the table).

## Part B — stat

1. **`back/core/deployRuns.ts`** (runs are derived at read time — merging also happens at read time, ingestion untouched):
   - `DEPLOY_STAGES` += `FLOW_START`, `FLOW_END`, `FLOW_ERROR`.
   - `fetchDeployRuns`: also select `stage LIKE 'FLOW_%' AND workflowRunId IS NULL` rows; group contiguous FLOW rows by (projectId, namespace) into flow groups; **merge rule**: attach a flow group to the earliest subsequent real run of the same project+namespace (group's timestamps after the previous run's last activity, before that run's MASTER_START); unmerged groups become **provisional runs** keyed `flow:<FLOW_START event id>` with `workflowRunId: null`, status derived from FLOW_ERROR presence.
   - Existing sort-by-last-activity already places them correctly.
2. **`web/src/deployTimeline.tsx`** — `buildTimelineItems` gets a new first item "flow" (before `master start`, line ~105) rendering its time + step chips (reuse the master chips pattern); `runStatus` (line 17): `FLOW_ERROR` → error, `FLOW_START` without `FLOW_END` → "flow running…".
3. **Redeploy button gating** — `web/src/components/DeployTab.tsx:410-416`: render the `run-retrigger` FeatureSlot only when the run has a real `workflowRunId`; same gating in the DivKit twin `back/core/miniEnvelope.ts:129-190`.
4. **`web/src/api.service.ts:27`** — DeployStage mirror += the three FLOW stages.

stat first (additive: `/add-event` already accepts unknown stages, old flow events keep working), then flow.
